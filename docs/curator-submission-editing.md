# Curator artwork and metadata corrections

Curators can open **Edit details** from a submission row, **Edit artwork and details** from a review, or the same link beside an accepted track in Publishing. The editor supports track title, release title and description, genres, moods, process tags and replacement artwork. A reason is required; artwork also requires the curator's explicit permission acknowledgement. Saving does not accept a review or publish a release.

The editor works before acceptance and on accepted, unpublished tracks, including submissions from before artwork intake existed. It preserves the artist's original submission, rights declaration, disclosure, provenance, private audio, final grade and review links. Corrections are separate append-only curator activity records. Accepted catalogue metadata changes in the same transaction as its audit note. On 17 October 2026 the maintainer explicitly approved audited corrections to genres, moods and process tags on published tracks. Accepted tracks whose track and release states are draft, in review or published expose this restricted discovery permission, including partial publication. Artwork, titles and release descriptions remain protected when full editing is unavailable. A restricted correction requires at least one genre, mood and process tag, a reason and the current revision. Withdrawn, rejected, archived and legacy release-only acceptances remain read-only. Artist identity, album membership, source audio and declarations remain outside this editor; Publishing retains its audited track-order tools.

Locked metadata selectors explicitly show “Read-only”, stay closed on mouse or keyboard activation, and close if saving disables the form. Editable selectors retain their selections when saving finishes. This prevents a locked editor from presenting checkboxes that cannot be selected.

The existing light/dark curator design system is reused. Storybook includes missing artwork, replacement, saving, stale conflict, read-only, published discovery correction, light theme and mobile stories. Inputs remain on validation failures. A stale revision is rejected instead of overwriting another curator's changes. Publication confirmation carries a release revision, checked again inside the atomic publisher. The loader retries if the revision changes while reading visible details. Identical publish retries retain the already-published URL. Editor saves return the revision inside the locked transaction. Pending tracks in an existing album show shared release title/description read-only until acceptance; this avoids saving overrides that would be discarded. A cleared shared description stays empty.

## Artwork and preparation

Covers are square JPG, PNG, WebP or AVIF, up to 20 MiB and 10000 pixels. Smaller square images resize in the browser to the existing 1400-pixel minimum without cropping. The server validates actual dimensions/type, fully decodes the exact bytes in the existing private encoder container, rejects corruption or animation, computes SHA-256 and asks R2 to verify the native checksum. New curator covers have unique private keys. Canonical and signed public delivery both require a published catalogue association. Artwork validation requires the private encoder binding and returns a visible retry error if unavailable or busy. They receive no published catalogue links until atomic publication. A lost database completion response never causes the uploaded object to be deleted; an unselected orphan can remain after an ambiguous outcome.

A curator replacement supplies the whole accepted release and is inherited when another track enters that album. Original artist cover records and permissions are retained separately. Existing curator artwork is recognized for older catalogue drafts. Private audio preparation can proceed while artwork is missing; publication still requires the verified fixed-profile streaming derivative, a ready cover, complete discovery metadata, exact accepted lineage and a complete ordered release.

## Published discovery corrections

The authenticated action checks discovery permission, protected text equality, complete tag selections and the current revision before accepting a restricted correction. The repository independently enforces these conditions under catalogue locks, in the same transaction as its append-only curator note, previous field values and publication audit entry. Restricted corrections update only the track's discovery columns and update timestamp. Release rows, title fields, lifecycle and publication dates, credits, media, original submission details and exact accepted review pins retain their saved values. Stale corrections, protected-field changes and artwork uploads are rejected without partial notes or audit entries.

Real PostgreSQL tests publish an accepted synthetic track, correct its discovery metadata, compare all protected records, verify the previous/current audit record, reject stale and forbidden payloads, and confirm the release remains publicly complete on retry. Action tests reject protected-field and artwork payloads before storage. Browser tests use the actual editor and CSS to select, search, remove and save tags, enforce read-only controls, and preserve choices across saving. No migration is required for this change. The affected live edit page requires deployment before its new discovery permission appears.

## PR review follow-up

Protected text is compared using the browser's representation before validation trims editable text or applies length limits. Multipart CRLF and textarea LF are equivalent for comparison; native single-line title inputs remove line breaks. Read-only title/release/description values then retain the exact stored strings for the repository's protected-field check and audit history, including surrounding whitespace. Shared read-only release fields before acceptance follow the same rule. Actual protected-text changes remain rejected, and editable descriptions use LF so multipart expansion does not change the character limit.

When the editor loses full editing permission, it clears pending artwork and its permission confirmation, displays the saved cover, and excludes artwork processing from discovery-only submissions. Regression cases reproduce the reported multipart failure, maximum-length multiline descriptions, unchanged whitespace, native title values, protected-text tampering and a selected file becoming read-only. A real multipart action-to-PostgreSQL correction verifies that the stored release description and all protected records remain unchanged.
