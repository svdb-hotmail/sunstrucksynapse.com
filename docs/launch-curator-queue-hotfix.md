# Curator queue production error — 14 October 2026

The maintainer's production screenshot showed the root error boundary at `/curator/submissions`. Cloudflare logs confirm HTTP 500 responses from deployed Worker version `2c9a0c44-8d18-441b-9bf1-4bd9bec166cb`; the stack fails in Neon HTTP reads of provenance sources/evidence while `listCuratorSubmissions` builds the queue. Authentication had already succeeded. The earlier anonymous Access-redirect health check did not exercise this path.

The production database was inspected read-only: six submissions, five provenance records and all thirteen migration journal entries. No production records, media, credentials, policies or schema were changed during diagnosis. The logs contain the failing stack but omit its underlying exception message, so they do not independently prove the provider's exact rejection reason.

The queue had an unbounded request multiplier: one list query followed by nine Neon HTTP queries for each complete submission, plus route counts, outbox, review audio and the root loader. An isolated PostgreSQL-compatible regression with 26 complete rows measures **235 queries** against the previous implementation. Each query uses a separate external fetch in production; this exceeds the 50-external-subrequest budget of a free Worker, and the current six-row production queue already needs at least 51 list/aggregate queries before the other loaders.

The fix loads each related table once for the entire page: submissions, invitations, latest rights/process/provenance versions, ordered steps/sources/evidence and activity. It uses PostgreSQL `DISTINCT ON` to select each submission's latest governance version and groups children by their exact parent IDs. Queue ordering, filtering, pagination, claim eligibility, private evidence projection and single-item review lookups are preserved. A full 26-row page now uses **ten queries**, independent of its row count. No provider, auth, storage, schema or publication policy changes are needed.

Focused verification: 17 tests across queue, curation workflow, evidence and invitation repositories passed, along with strict TypeScript and touched-source ESLint. The new regression fails against the previous implementation specifically on its query budget (235 versus at most ten); its search and missing-record checks already pass there. It verifies latest versions, exact per-submission child associations, evidence metadata, ordering, search, pagination and single review reads against actual migrated PGlite databases. Production deployment and the maintainer's authenticated refresh must still confirm recovery; an anonymous redirect alone is insufficient.

The maintainer's SOLO exception remains active. No Village agents or independent review claims are used. This fix continues the explicitly authorized implementation, review-comment resolution, merge and production deployment for the maintainer's own E2E validation.
